# 配置结构演进：Legacy (V1) vs Current (V9)

本文档对比了 AIGen-UI 项目的旧版配置结构 **Legacy (V1)** 与当前的架构 **V9 (Module-Clustered)**。

---

## 1. 旧配置结构 (Legacy V1)

旧结构将所有信息（导航、页面配置、样式）打包在一个巨大的 JSON 对象中。

### 数据模型

```json
{
  "version": "1.0",
  "navGroups": [
    {
      "items": [
        {
          "id": "nav-1",
          "title": "销售管理",
          "items": [
            {
              "id": "page-1",
              // 🔴 痛点：页面配置直接耦合在导航节点中
              // 当页面增多时，导航数据体积无限膨胀
              "component": {
                "filterArea": { ... },
                "tableArea": { ... }
              },
              "template": "Page1"
            }
          ]
        }
      ]
    }
  ],
  // 🔴 痛点：冗余且不清晰的顶层字段
  "pageConfigs": {} 
}
```

### 缺点
1.  **性能瓶颈**: 即使只需要显示左侧菜单，也必须从数据库拉取通过几 MB 的完整配置（包含所有表格列、筛选项定义）。
2.  **更新冲突**: 修改一个页面的表格列宽，需要保存整个大 JSON，容易覆盖其他未知的配置变更。
3.  **扩展性差**: 难以支持“仅加载当前页面配置”的优化。

---

## 2. V9 架构：基于模块的聚合存储 (Module-Clustered Architecture)

V9 方案融合了 V1 的原子性优势和按需加载的理念，旨在解决单体应用膨胀和过度拆分带来的问题。

### 核心思想
**"按一级导航 (Module) 聚合配置"**。
不再让每个页面 (Page) 成为数据库中的孤岛，也不像 V1 那样全量打包。而是以**一级菜单** (Level 1 Nav) 为单位，将其下属的所有二级菜单页面的配置存储在同一行记录中。

### 数据库表结构设计 (Dedicated Tables)
摒弃通用的 KV 表 `user_configs`，使用语义更清晰的专用业务表：

1.  **`team_configs`**
    *   一行代表一个用户的团队/项目集配置。
2.  **`menu_configs`**
    *   一行代表一个用户的完整导航树结构。
3.  **`page_configs`** (核心变更)
    *   **粒度**：一行 = 一个一级导航项 (Level 1 Nav Item)。
    *   **内容**：包含该一级导航下**所有**二级导航页面的配置。

| 字段名 | 类型 | 说明 |
| :--- | :--- | :--- |
| `id` | UUID | 主键 |
| `user_id` | UUID | 所属用户 |
| `nav_id` | String | 一级导航 ID (如 `nav-sales`) |
| `configs` | JSONB | Map 结构: `{ "sub-page-1": {...}, "sub-page-2": {...} }` |

---

## 3. V1 与 V9 核心对比

| 维度 | Legacy (V1) | Current (V9) | 解析 |
| :--- | :--- | :--- | :--- |
| **存储方式** | 单体 JSON (Monolithic) | 模块聚类 (Module Clustered) | V9 避免了单文件无限膨胀，同时避免了碎片化。 |
| **数据粒度** | 整个应用一个大对象 | 按一级导航 (Module) 聚合 | V9 的粒度适中，既方便管理又提升性能。 |
| **数据库表** | `user_configs` (单记录) | `team_configs` (项目), `menu_configs` (导航), `page_configs` (页面) | V9 使用专用表，利用数据库索引优化查询。 |
| **加载性能** | 慢 (一次性全量加载) | 均衡 (按模块加载) | V9 进入模块时拉取该模块所有页面，后续切换无延迟。首屏仅需加载导航，速度更快。 |
| **状态维护** | 简单 (原子性高) | 简单 (模块内原子性) | V9 像 V1 一样容易维护数据一致性，修改某模块配置只需更新该模块对应记录。 |
| **更新冲突** | 高风险 (全量覆盖) | 低风险 (模块隔离) | V9 下不同模块的修改互不影响，降低了多人协作冲突概率。 |
